# Task 5 — upload và vòng đời phiên multipart

Đã triển khai mã production:

- API mở phiên, ký URL từng part, hoàn tất và hủy phiên multipart trên S3. Khóa object do máy chủ tạo theo tenant/file/version; URL part sống tối đa 10 phút; phiên sống 1 giờ. `Upload:MaxStorageBytes` mặc định 50 GiB, phải là số dương. Giới hạn này độc lập với giới hạn phân tích 100 MiB. API complete chỉ nhận part number và ETag; đọc HEAD để kiểm tra kích thước, loại nội dung an toàn `application/octet-stream`, không tải thân file vào API.
- Begin gắn hash của tên/kích thước/folder/file thay thế với Idempotency-Key. Complete gắn hash danh sách part đã sắp xếp với phiên trước khi gọi S3. Pending→Completing với owner/lease 30 phút diễn ra trước tác động S3; request thứ hai không được chiếm lease còn hiệu lực hoặc gọi S3 song song. Callback chỉ nhận đúng owner còn lease, abort không dọn phiên Completing. Nếu S3 đã complete nhưng mất phản hồi, request đang giữ lease kiểm tra HEAD. Worker hết lease chuyển terminal rồi tiếp tục dò object muộn không giới hạn thời gian. Quota logic ghi SQL delta theo tenant→department→user→provider; replacement chỉ giữ phần tăng ròng, nên thay file cùng kích thước không cần quota logic trống. `Upload:MaxStagingBytesPerProvider` mặc định 200 GiB giới hạn riêng dung lượng tạm theo provider. Quota của chủ file được dùng khi Editor thay nội dung.
- Complete ghi `FileEntry`, `FileContentVersion` ở trạng thái `Pending`, document outbox `DocumentCreated`/`DocumentContentChanged`, và mutation authorization global cùng transaction. Nội dung chưa được đọc cho tới khi worker Task 7 xác minh quét và kiểu file rồi đánh dấu version `Clean`. Quyền bắt đầu/ký part/hoàn tất lấy session tenant và snapshot file.upload hiện hành; folder cần quyền ghi, file thay thế cần file.update. Callback đọc lại envelope Redis, trạng thái phiên, grant mục tiêu hiện hành và scope/user version trước khi ghi; scope mới version 0 được chấp nhận khi DB chưa có hàng.
- Worker 5 phút hết hạn phiên, hoàn quota và staging một lần rồi abort/xóa object. Worker cũng liệt kê multipart S3 quá 2 giờ không có phiên bền vững để dọn orphan sau lỗi begin/SQL. Migration cộng thêm trạng thái phiên, counter staging provider và bảng intent legacy; không đổi dữ liệu/bảng không liên quan; chưa chạy migration trên DB người dùng.
- Upload cũ tạo intent bền vững trước khi gửi object; S3/Local dùng khóa biết trước, Google Drive/OneDrive dùng marker riêng để tìm object. Callback đổi intent sang Committed cùng file/version/outbox; worker chỉ giữ object có content version tham chiếu đúng provider/key, xóa object không được tham chiếu và dò lại object muộn không giới hạn thời gian. Upload cũ dùng kiểm tra snapshot hiện hành, ClamAV chỉ nhận đúng phản hồi `stream: OK`, tạo trusted version `Clean` với MIME trung tính `application/octet-stream` và document outbox trong authorization coordinator. Quét tắt, timeout, lỗi kết nối và phản hồi sai đều từ chối. Event `DocumentPermissionsChanged` được ghi cùng mutation quyền; lifecycle đã ghi event từ Task 3.

Vòng dọn dẹp ghi thời điểm thử sau cả thành công lẫn thất bại, chọn theo thời điểm cũ nhất và không loại hàng sau 48 giờ. `NoSuchUpload` khi abort S3 là kết quả idempotent. Với replacement, version cũ giữ `RetainedStagingBytes` trong giới hạn staging sau khi quota logic chuyển sang version mới; `PhysicalStorageDeletedAt` là dấu CAS để Task 7 xóa object cũ rồi gọi `UploadQuota.RecordPhysicalCleanupAsync` trong cùng giao dịch SQL nhằm hoàn staging đúng một lần. Nếu staging của provider cũ đầy, complete không xuất bản file mới; worker xử lý object chưa commit. File cũ chưa có `FileContentVersion` khớp provider/key/kích thước bị từ chối trước khi mở multipart; Task 7 cần hòa giải và xác minh version lịch sử trước khi cho phép thay thế.

`DocumentMetadataChanged` chưa có trigger vì baseline chưa có use case sửa metadata file. Khi thêm use case đó, ghi event cùng transaction cập nhật metadata; không tạo endpoint CRUD mới trong Task 5.

Hợp đồng cho Task 7: xử lý event của version `Pending` bằng luồng từ object storage, kiểm tra hash/scan/MIME thực tế và chỉ đổi sang `Clean` khi xác minh thành công; giữ `Failed`/`Infected` không đọc được. Với upload cũ đã quét sạch, xác minh MIME thực tế trước khi thay `application/octet-stream` để cho phép hiển thị inline. Sau scan sạch, cập nhật `FileEntry.ScanStatus`/hash/content type và xuất bản quyền/trạng thái theo compare-and-publish để event version cũ không mở lại file đã xóa hoặc ghi đè. Với replacement, version cũ còn lưu vật lý nhưng quota logic đã chuyển sang kích thước version mới; quy trình retention/physical cleanup phải tách khỏi hoàn quota logic `QuotaReleasedAt`.

Kiểm chứng mã: `dotnet build src/CleanArchCqrs.API/CleanArchCqrs.API.csproj --no-restore --verbosity quiet` thành công, 0 lỗi; còn 3 cảnh báo có sẵn về PackageReference trùng và GoogleCredential cũ. `git diff --check` không thấy lỗi whitespace. Chưa viết/chạy test, integration hoặc benchmark theo chỉ đạo người dùng.

Kiểm thử để làm trong pha cuối: begin cùng/different payload; manifest part sai/trùng/khác trên retry; tenant/owner/folder ACL/session hết hạn hoặc bị thu hồi, gồm Redis chặn trước khi DB cập nhật và grant tự hết hạn; scope global bootstrap version 0; S3 complete mất phản hồi hoặc hoàn tất sau timeout; HEAD thiếu/sai kích thước; complete/abort/expiry đồng thời; quota cạnh tranh upload/purge trên provider chung; replacement cùng kích thước khi quota đầy, provider đổi và staging đầy; ClamAV disabled/error; retry/outbox/projection; MinIO multipart và orphan cleanup; intent legacy có commit không rõ kết quả trên bốn provider; migration fresh/upgrade giữ các cột legacy. Cần kiểm tra riêng ba assertion cũ của `FileUploadSecurityTests` về SystemAdmin/thông điệp quota bằng hành vi an ninh thực tế.
