# Task 5 — upload và vòng đời phiên multipart

Đã triển khai mã production:

- API mở phiên, ký URL từng part, hoàn tất và hủy phiên multipart trên S3. Khóa object do máy chủ tạo theo tenant/file/version; URL part sống tối đa 10 phút; phiên sống 1 giờ. `Upload:MaxStorageBytes` mặc định 5 GiB, phải là số dương. Giới hạn này độc lập với giới hạn phân tích 100 MiB. API complete chỉ nhận part number và ETag; đọc HEAD để kiểm tra kích thước, loại nội dung an toàn `application/octet-stream`, không tải thân file vào API.
- Begin gắn hash của tên/kích thước/folder/file thay thế với Idempotency-Key. Complete gắn hash danh sách part đã sắp xếp với phiên trước khi gọi S3; retry chỉ nhận cùng manifest. Nếu S3 đã complete nhưng mất phản hồi, retry kiểm tra HEAD. Pending→Completed và Pending→Failed/Expired dùng cập nhật SQL có điều kiện trên cùng hàng; chỉ trạng thái terminal Failed/Expired mới được xóa object. Quota được ghi bằng SQL delta theo tenant→department→user→provider, có giới hạn cả bốn tầng; thay thế tính phần cũ/phần mới và giữ quota của chủ file khi Editor thay thế.
- Complete ghi `FileEntry`, `FileContentVersion` ở trạng thái `Pending`, document outbox `DocumentCreated`/`DocumentContentChanged`, và mutation authorization global cùng transaction. Nội dung chưa được đọc cho tới khi worker Task 7 xác minh quét và kiểu file rồi đánh dấu version `Clean`. Quyền bắt đầu/hoàn tất lấy session tenant và snapshot file.upload hiện hành; folder cần quyền ghi, file thay thế cần file.update; callback đối chiếu phiên/user/scope version trước khi ghi.
- Worker 5 phút hết hạn phiên, hoàn quota một lần rồi abort/xóa object. Worker cũng liệt kê multipart S3 quá 2 giờ không có phiên bền vững để dọn orphan sau lỗi begin/SQL. Migration chỉ thêm cột phiên, không đổi dữ liệu/bảng không liên quan; chưa chạy migration trên DB người dùng.
- Upload cũ dùng kiểm tra snapshot hiện hành, ClamAV chỉ nhận đúng phản hồi `stream: OK`, tạo trusted version `Clean` và document outbox trong authorization coordinator. Quét tắt, timeout, lỗi kết nối và phản hồi sai đều từ chối. Event `DocumentPermissionsChanged` được ghi cùng mutation quyền; lifecycle đã ghi event từ Task 3.

`DocumentMetadataChanged` chưa có trigger vì baseline chưa có use case sửa metadata file. Khi thêm use case đó, ghi event cùng transaction cập nhật metadata; không tạo endpoint CRUD mới trong Task 5.

Hợp đồng cho Task 7: xử lý event của version `Pending` bằng luồng từ object storage, kiểm tra hash/scan/MIME thực tế và chỉ đổi sang `Clean` khi xác minh thành công; giữ `Failed`/`Infected` không đọc được. Sau scan sạch, cập nhật `FileEntry.ScanStatus`/hash/content type và xuất bản quyền/trạng thái theo compare-and-publish để event version cũ không mở lại file đã xóa hoặc ghi đè. Với replacement, version cũ còn lưu vật lý nhưng quota logic đã chuyển sang kích thước version mới; quy trình retention/physical cleanup phải tách khỏi hoàn quota logic `QuotaReleasedAt`.

Kiểm chứng mã: `dotnet build src/CleanArchCqrs.API/CleanArchCqrs.API.csproj --no-restore --verbosity quiet` thành công, 0 lỗi; còn 3 cảnh báo có sẵn về PackageReference trùng và GoogleCredential cũ. `git diff --check` không thấy lỗi whitespace. Chưa viết/chạy test, integration hoặc benchmark theo chỉ đạo người dùng.

Kiểm thử để làm trong pha cuối: begin cùng/different payload; manifest part sai/trùng/khác trên retry; tenant/owner/folder ACL/session hết hạn hoặc bị thu hồi; Redis outage/pending; S3 complete mất phản hồi; HEAD thiếu/sai kích thước; complete/abort/expiry đồng thời; quota cạnh tranh upload/purge trên provider chung; replacement/version cũ; ClamAV disabled/error; retry/outbox/projection; MinIO multipart và orphan cleanup; migration fresh/upgrade giữ các cột legacy. Cần kiểm tra riêng ba assertion cũ của `FileUploadSecurityTests` về SystemAdmin/thông điệp quota bằng hành vi an ninh thực tế. Cần chính sách bucket dọn orphan cho upload cũ nếu transaction commit có kết quả không rõ ràng sau khi đã ghi object vì luồng cũ chưa có bản ghi intent bền vững trước khi gửi object.
